# donald — microk8s deployment

Deploys the generated Go app (`../backend/donald`) onto the Linode box **donald**
(`45.33.12.143`, us-central, `g6-dedicated-2` — 2 dedicated vCPU / 4 GiB RAM /
Ubuntu 24.04), with MySQL in-cluster on the same node.

| Hostname | Serves | Helm release |
| --- | --- | --- |
| `api.usedonald.com` | generated REST API + SSE stream `GET /v1/runs/{run_key}/stream` | `donald-api` (`DONALD_ROLE=api`) |
| `mcp.usedonald.com` | MCP endpoint at **`/v1/mcp`** | `donald-mcp` (`DONALD_ROLE=mcp`) |
| `usedonald.com` | React frontend — **not built yet**, placeholder page | `donald-web` |

All three DNS names already resolve to `45.33.12.143` (verified).

## One image, two releases

`donald-api` and `donald-mcp` are two installs of the **same chart** (`.helm/donald`)
running the **same image**. They differ only in `DONALD_ROLE`, which
`app/mcp/server.go:RoleFromEnv` reads to pick which half of the HTTP surface to mount:

- `api` → generated CRUD + `GET /v1/runs/{run_key}/stream`
- `mcp` → generated CRUD + `/v1/mcp` and `/v1/mcp/*`
- `all` → both, and the fallback when the variable is unset or unrecognised, so a
  misconfigured pod is unisolated rather than down.

The split buys blast-radius isolation, not correctness: agent traffic is bursty
and must not slow the REST API the web app depends on. Each release gets its own
process, connection pool and resource limits; `donald-mcp` gets the larger budget
because it absorbs the agents. Both talk to the **same** MySQL.

**Replicas.** Either release is safe to scale past 1 — browser deltas come from
tailing the `agent_event` table, not an in-process channel, so an event written
by an MCP pod reaches a browser attached to any API pod. Both sit at
`replicaCount: 1` with `autoscaling.enabled: false` (house convention, and the
node is only 2 vCPU).

## Layout

Charts follow the `helm create` scaffold used throughout `nuzur-go/.helm`
(`Chart.yaml`, `values.yaml`, `templates/{deployment,service,ingress,hpa,serviceaccount,NOTES.txt,_helpers.tpl,tests/}`),
with the same conventions: `service.type: ClusterIP`, `ingress.className: "nginx"`,
`cert-manager.io/cluster-issuer: lets-encrypt`, resources always setting both
limits and requests, `serviceAccount.create: true`.

```
deploy/
  deploy.sh                 # run from the laptop: sync + build + install + verify
  schema.sql                # the 7-table DDL, generated by nuzur (see below)
  cluster-issuer.yaml       # ClusterIssuer `lets-encrypt` (+ staging)
  prod.yaml.example         # template for the config overlay; the real one is box-only
  .helm/
    donald/                 # the Go app chart — installed TWICE
      values.yaml           #   shared defaults (role: all, never installed alone)
      values-api.yaml       #   release donald-api
      values-mcp.yaml       #   release donald-mcp
    donald-web/             # placeholder frontend
    donald-mysql/           # in-cluster MySQL 8.4
  scripts/
    00-open-ssh-2222.sh     # paste into LISH — see "SSH access"
    01-bootstrap-box.sh     # microk8s + addons + ingress-nginx + docker
    02-build-image.sh       # docker build + import into containerd
    03-deploy.sh            # secrets + overlay + helm installs + schema + verify
    linode-cloud-config.yaml# alternative: cloud-init for a Linode rebuild
```

No secret is in this directory. Passwords are generated on the box into
root-only `/etc/donald/credentials.env` and flow from there into the `donald-db`
Secret and the config overlay.

## SSH access

`ssh root@45.33.12.143` on **port 22** with `~/.ssh/id_ed25519`. That is what
`deploy.sh` uses.

For a while during authoring, port 22 to Linode was unreachable from the laptop's
network — the TCP handshake completed and the SSH banner never arrived, on this
box and on the account's other one, while `github.com:22` answered instantly.
That has since cleared. If it ever comes back, the fallback is to put sshd on a
second port from the LISH console: `scripts/00-open-ssh-2222.sh` does that
(Ubuntu 24.04 socket-activates sshd, so adding a `Port` line alone is not enough
— the script hands the listener back to `ssh.service`), and `deploy.sh` takes
`SSH_PORT=2222`. `scripts/linode-cloud-config.yaml` is the same thing as
cloud-init for a rebuild — note a rebuild **wipes the box**, including the
authorized key.

## Deploying

```sh
cd deploy
./deploy.sh                    # full run
./deploy.sh --skip-bootstrap   # subsequent runs
```

Overridable: `HOST`, `SSH_PORT` (default **2222**), `SSH_USER`, `SRC`, `TAG`.

What it does:

1. `rsync`s `backend/donald`, `.helm/`, `schema.sql` and `cluster-issuer.yaml` to
   `/opt/donald` on the box.
2. `01-bootstrap-box.sh` — installs docker (image builder only), microk8s 1.31,
   the `dns`, `hostpath-storage`, `cert-manager` and `helm3` addons, and
   ingress-nginx from its own chart.
3. `02-build-image.sh` — `docker build` on the box (native amd64; the laptop is
   arm64), then `docker save | microk8s ctr image import -`, then **verifies** the
   image is actually in containerd.
4. `03-deploy.sh` — generates/reuses the passwords, writes the config overlay,
   creates the `donald-db` Secret, installs `donald-mysql`, **applies `schema.sql`
   and verifies all 7 tables**, applies the issuers, installs `donald-api`,
   `donald-mcp` and `donald-web`, and runs an in-cluster smoke test.
5. Curls all three hostnames from the laptop.

### Redeploy after a code change

```sh
cd deploy && ./deploy.sh --skip-bootstrap
```

**A redeploy fails safe.** If the app does not compile, `docker build` exits
non-zero, `02-build-image.sh` stops, and `deploy.sh` aborts before helm is
touched — the running pods keep serving the previous image. Observed, not
assumed: a redeploy attempted mid-edit failed on
`app/mcp/nodes.go:198: undefined: null` and the cluster stayed on its existing
tag with zero restarts. Nothing is rolled forward until there is a working
binary, so it is safe to retry whenever the tree builds again.

### Images — no registry, so mind the tag

The user chose local build + import over GHCR, which has two consequences the
charts encode:

- `image.pullPolicy: IfNotPresent` (**not** the house default `Always`) and
  `imagePullSecrets: []`. There is nothing to pull from; `Always` would give
  `ImagePullBackOff`.
- **Every build gets a unique tag** (a timestamp), passed to helm with
  `--set image.tag=`. With `IfNotPresent` and a mutable tag like `latest`, a
  re-import leaves the kubelet running the old layers and you spend an hour
  debugging a fix that was never deployed.

microk8s does **not** read the host Docker daemon's image store — that is the
classic failure here — so `02-build-image.sh` imports into containerd and then
asserts `docker.io/library/donald:<tag>` is listed before the deploy proceeds.

Moving to GHCR later is a values change plus a workflow: set `image.repository`,
`pullPolicy: Always`, and restore `imagePullSecrets: [{name: ghcr-login-secret}]`.

### Ingress class: why not the microk8s `ingress` addon

The addon *is* ingress-nginx, but it registers its IngressClass as **`public`**,
while every chart in this org sets `ingress.className: "nginx"`. Rather than make
this box the odd one out, `01-bootstrap-box.sh` installs ingress-nginx from its
own chart as a DaemonSet on hostPorts 80/443, with
`controller.ingressClassResource.name=nginx`. The
`nginx.ingress.kubernetes.io/...` annotations behave identically either way.

## Configuration

`config.New()` reads `CONFIG` — the app **exits** if it is unset, there is no
default — and `ENV`, which the Dockerfile already bakes to `prod`. Both releases set:

```
CONFIG=/root/config,/root/hostconfig/nuzur/donald
```

Following the `product` chart, the overlay comes from a **hostPath**, not a
Secret: `/etc/config` on the node, mounted into the pod.

> ### ⚠️ donald mounts at `/root/hostconfig`, not `/root/config`
> The `product` chart mounts the hostPath at `/root/config` because product's own
> config lives at `/root/product/config`. **Donald is different**: its Dockerfile
> does `WORKDIR /root/` then copies the source tree, so donald's own `base.yaml`
> is at **`/root/config/base.yaml`** — exactly the path product mounts over.
> Mounting there would shadow `base.yaml`, which is what supplies
> `ports.http: 8080`, and the failure would look nothing like a config problem.
> Same convention, different mount point. Do not "fix" it back.

So the real file goes at `/etc/config/nuzur/donald/prod.yaml` (root-owned, `chmod
600`, written by `03-deploy.sh`) and appears in the pod at
`/root/hostconfig/nuzur/donald/prod.yaml`. `prod.yaml.example` is the committed
template; the real one is never committed.

`base.yaml` ships with literal `<< Database Name Here>>` placeholders, so the
overlay is mandatory. `params: "parseTime=true&interpolateParams=true&charset=utf8mb4"`
— **`parseTime=true` is not optional**: every entity has `created_at`/`updated_at`
and the driver cannot scan DATETIME without it.

### Known gap: R2 credentials — uploads are non-functional

`R2_KEY_ID` and `R2_SECRET` in `/etc/donald/credentials.env` are **empty** — nobody
supplied them.

Measured behaviour on the live box, not assumed. The bucket name *is* set, so
`storage.NewClient` succeeds and `storage.Register` logs the cheerful
`storage: mounted /upload and /sign on the http port`; the failure happens at
request time instead:

```
POST /upload -> HTTP 500   {"error":"upload failed"}
log: operation error S3: PutObject, get identity: get credentials:
     failed to refresh cached credentials, static credentials are empty
```

So it is **500, not 503** — the 503 path only applies when the bucket itself is
blank. Everything else is unaffected: CRUD, all 13 MCP tools and the SSE stream
work. Artifact *rows* can be created; only the bytes have nowhere to go.

Fixing it is a config edit plus a restart, **not** a redeploy:

```sh
ssh root@45.33.12.143
vi /etc/donald/credentials.env          # fill R2_KEY_ID and R2_SECRET
/opt/donald/scripts/03-deploy.sh        # rewrites the overlay + reinstalls
microk8s kubectl -n donald rollout restart deploy/donald-api deploy/donald-mcp
```

(Editing `/etc/config/nuzur/donald/prod.yaml` directly and restarting the two
deployments works too — the overlay is a hostPath file, so no image rebuild and
no new tag are involved.)

## Health probes

The generated router **does** register `GET /healthz` (`rest/server/router.go`),
returning `{"status":"OK"}` without touching the database — used for liveness and
startup, so a DB blip cannot trigger a restart loop.

Readiness is `GET /v1/clients?page_size=1`, a real query, so a pod only takes
traffic once MySQL is reachable **and** the schema is applied — which keeps a pod
with no tables out of the Service. (The parameter is `page_size`, not `limit` —
see `rest/server/list_params.go`.)

Both were confirmed against the real image before being written into the charts.

## The database schema

`schema.sql` is the real nuzur DDL for published version `v2-run-graph-events`
(`5cb1a21a-264d-4108-8170-4bf8b1109058`), produced with

```sh
nuzur-cli deploy --plan --json --project donald --version v2-run-graph-events \
  --local-agent <agent-uuid> --local-agent-connection <connection-uuid>
```

and taking the `apply_sql` field. The plan reported **7 statements, all additive,
`destructive: false`**. Note `--plan` refuses a bare `--db-dsn` ("the diff runs
either through a box's agent or against a nuzur team connection"), which is why
the local-agent route was used. To regenerate after a schema change, publish the
new version and rerun.

`03-deploy.sh` applies it with `kubectl exec` into the MySQL pod, then asserts all
7 tables are present (failing the deploy otherwise) and proves the `donald` app
user — not just root — can read them.

Optional: to point the nuzur data manager at this database, run
`nuzur-cli deploy --db-only --db-dsn ... --provider ssh --host 45.33.12.143 --port 2222`
against a port-forward of the MySQL Service. Not required, and not done here.

## TLS

cert-manager (microk8s addon) with the **`lets-encrypt`** ClusterIssuer — that
exact name, matching every chart in `nuzur-go/.helm`; `letsencrypt-prod` would
silently never issue anything. HTTP-01 over the `nginx` ingress class. Each
hostname gets its own certificate: `donald-api-tls`, `donald-mcp-tls`,
`donald-web-tls`.

If a certificate does not go Ready, point the charts' annotation at
`lets-encrypt-staging`, confirm the challenge path works, then switch back —
Let's Encrypt rate-limits failed production validations hard.

```sh
microk8s kubectl -n donald get certificate
microk8s kubectl -n donald describe certificate donald-api-tls
microk8s kubectl -n donald get challenge
```

## SSE / streaming ingress settings

`values-api.yaml` and `values-mcp.yaml` both set the three annotations the `ccmcp`
chart already uses for exactly this reason:

```yaml
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-buffering: "off"
```

The api host needs them for `GET /v1/runs/{run_key}/stream`; the mcp host needs
them because MCP's streamable-HTTP transport holds a long-lived SSE GET on
`/v1/mcp`. nginx's default 60 s read timeout would close an idle stream (the app
sends a keepalive comment every 20 s, but the timeout still has to outlive a quiet
run) and the graph would appear frozen and then jump. Buffering off means SSE
bytes are flushed rather than held — the app already sends `X-Accel-Buffering: no`,
this makes it explicit.

## Demo data left in the database

Verifying the deploy end to end wrote one real run through the public MCP
endpoint, so the database is not empty:

- `client`: 1 row, `Donald demo tenant` (created on demand by `app/mcp/handler.go`)
- `agent_run`: 1 row, `run_key = deploy-verify-1`
- `agent_node`: 2 rows (`build`, `deploy`), `agent_event`: 3 rows

Harmless, and handy for the frontend to render against. To clear it:
`DELETE FROM agent_run WHERE run_key = 'deploy-verify-1';` (nodes, edges and
events cascade).

## Caveats

- Single node, single MySQL replica on a hostpath PVC. No HA, no backups.
- No Linode Cloud Firewall is attached. Only 80/443 and SSH are meant to be
  reachable, but nothing enforces that — add a firewall if this outlives the demo.
- Auth is disabled by design (hackathon demo). `api.` and `mcp.` are open to the
  internet, and `/v1/mcp` lets any caller write runs into the demo tenant.


## Deploying the web app

Separate from the backend deploy on purpose — the frontend and backend are worked
on by different people, and neither should have to rebuild the other to ship.

```sh
cd deploy && ./deploy-web.sh
```

It rsyncs `../frontend` (minus `node_modules`/`.next`, which are large and
platform-specific), builds `web.Dockerfile` on the box, imports the image into
containerd, and upgrades the `donald-web` release.

**The Dockerfile lives in `deploy/`, not `frontend/`** — the frontend tree is
actively edited by others, and a build file dropped in there is a merge conflict
waiting to happen. The build context is still the frontend directory.

**`NEXT_PUBLIC_DONALD_API` is baked in at BUILD time**, so pointing the app at a
different API is a rebuild, not a restart. It currently defaults to EMPTY, which
makes the app play its recorded fixture — a working demo. Setting it today would
ship a broken site, because `lib/donald/source.ts`'s `apiSource` targets
endpoints that do not exist (`agent_events`, `sequence_gt`). Once that is
rewritten against the real endpoints:

```sh
API=https://api.usedonald.com ./deploy-web.sh
```

Endpoints the web app should use (all live now):

| Endpoint | Purpose |
|---|---|
| `GET /v1/runs` | run list, newest first |
| `GET /v1/runs/{run_key}` | snapshot: run + nodes + edges, plus `last_sequence` |
| `GET /v1/runs/{run_key}/stream?after=N` | SSE deltas after a cursor |
| `POST /v1/runs/{run_key}/interventions` | raise stop/steer — `{type, node_key?, prompt}` |

Verified on the box: the image builds, runs as the unprivileged `node` user,
serves `/` and `/api/donald-recording`, is ready in ~350ms, and inlines the API
base into the client bundle. Image is ~990 MB because it carries `node_modules`;
switching `next.config.mjs` to `output: 'standalone'` would cut that
substantially, and is worth doing once the frontend settles.
